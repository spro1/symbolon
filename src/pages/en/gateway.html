Sign-in and access checks
for your internal services

Symbolon Gateway sits in front of your internal web services. It opens them on HTTPS addresses and, on every request, checks who the user is and whether they have access before passing the request on. You don't need to change the services.

Service registration

Enter an address and a domain
to register a service

Enter the service's internal address and the internal domain to use, and the registration screen walks you through the rest. Certificates are issued automatically and renewed before they expire.

Access policy

Decide who can reach
what

  • Choose per service whether users must sign in, or whether it is an API called with tokens only.
  • Choose the groups allowed in. Sensitive paths, such as admin pages, can have their own policy.
  • Require two-step verification again for important paths.
  • Policies set for an organization or environment apply to the services under it.
  • Before a policy takes effect, check whether a given user would get in.

Change management

Changes are checked and approved
before they take effect

Services and policies aren't edited in place. Changes are grouped, checked and then applied, which makes it harder to widen access by mistake.

  1. 1

    Draft

    Collect changes such as a new service or an added group.

  2. 2

    Check

    Find domain or policy conflicts and groups that don't exist before anything is applied.

  3. 3

    Approve

    Production changes are approved by an administrator other than the author.

  4. 4

    Deploy

    Approved changes are applied to every gateway.

  5. 5

    Roll back

    If something goes wrong, return to the previous state right away.

Changes that widen access

Need a security officer's approval

Changes that widen access, such as turning off sign-in or adding an allowed group, take effect only after a security officer approves them.

Changes that narrow access

Can go out right away in an emergency

Changes that block access, such as turning on sign-in or removing a group, can be applied immediately without approval, with a reason recorded.

Sign-in server integration

Works with Symbolon ID
out of the box

With Symbolon ID, the settings needed to connect the two are created for you. You can also connect a standard OIDC sign-in server you already use.

Settings created for you

Turn on sign-in for a service and the Symbolon ID settings are created automatically. Settings that drift are corrected regularly.

Group search

Search Symbolon ID's groups while writing an access policy. You are warned if a policy uses a group that was deleted.

Sign-out everywhere

Signing out of Symbolon ID, or disabling an account, signs the user out of every internal service.

Monitoring

See allowed and denied
requests as they happen

The dashboard shows total requests and how many were allowed, sent to sign-in or denied. Denied requests are recorded with the user, path and reason.

Traffic map

Shows which services requests are flowing to. Color it by requests, error rate, response time or denied access.

Anomaly alerts

The console raises an alert when errors or response times rise well above normal.

Audit log

Every administrative action is recorded, and you can verify in the console that the log hasn't been altered.

Operations

Arrange it to fit
your environment

Symbolon Gateway can be used on its own. You can even start with internal domains and HTTPS only, without sign-in.

Gateway groups

Run services with different security levels or network zones on separate gateway groups.

Uninterrupted access

Users can keep using internal services while the management server is under maintenance.

Separate admin accounts

The console uses its own administrator accounts, so you can still manage the gateway if the sign-in server has a problem.

Try it first
on a single machine

The evaluation install puts both products and a sample service on one machine. To try it, open a GitHub issue.
