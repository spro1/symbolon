Security principles

Requests that can't be verified
don't get through

Symbolon Gateway and Symbolon ID are designed so that an outage never results in unauthorized access. This page describes the principles both products follow.

Security review

An independent security review, three rounds of fixes and re-verification are complete; as of release there are no known issues of high severity or above. Details on request.

This does not mean there are no vulnerabilities, or that the products hold a security or compliance certification. Customers evaluating Symbolon can receive the review results separately.

Access control

Principles that protect
requests to your services

{{include name="i-ban"}}

Block when unsure

If an outage prevents checking sign-in or access, the request is blocked and a notice page is shown. There is no setting that lets users in without sign-in during an outage.

{{include name="i-eye"}}

Only verified user details

Services receive only user details the gateway has verified itself. User details forged from outside never reach the service.

{{include name="i-globe"}}

Separate sign-in state per service

Sign-in state is kept separately for each service. Sign-in data from one service can't be used with another.

{{include name="i-server"}}

Only to allowed servers

The gateway sends requests only to internal servers an administrator has allowed. Each organization has its own list.

Administration

A password alone doesn't
give admin rights

In both products, administrator accounts require two-step verification. Important changes can't be applied by one person alone.

A second pair of eyes

Production changes are approved by an administrator other than the author. Changes that widen access need a security officer's approval.

Signed configuration

The gateway applies only configuration signed by the management server. Configuration altered along the way is rejected.

Audit log

Every administrative action is recorded, and you can verify that the log hasn't been changed or deleted.

Protected secrets

Secrets used for integrations are stored encrypted. The two products keep separate accounts and data, so a problem in one doesn't spread to the other.

Development and release

No release with
known vulnerabilities

We use external libraries only where needed. Dependencies are scanned before each release, and any known vulnerability blocks the release.

Automated tests close to real use

Tests run the real programs and database and check behavior under outages and attacks as well as normal use.

Real browser tests

The admin console is opened screen by screen in a real browser to catch errors and accessibility problems.

Reporting a security problem

Found a security problem?

GitHub issues are public. Please don't post details of a security problem in an issue; ask first how to send it privately.

What we ask of you when deploying

  • Set up the network so internal services accept only requests that come through the gateway.
  • Set up two-step verification as soon as you create an administrator account.
  • Review the audit log regularly.
